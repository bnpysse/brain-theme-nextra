很多工程领导近期最关心的一件事就是如何应对代码审查负载的持续增加。这是一个老生常谈的话题，但最近越来越多这样的讨论在进行。

对我而言，这一问题始于一月份，当时 Opus 4.5 和 GPT 5.4 在大多数公司开始编写更多的高质量代码。大约在这个时候，总监级别的人员开始谈论软件从编码阶段过渡到审查阶段时遇到的瓶颈问题。

自二月以来，为了应对增加的负载，AI 代码审查工具得到了蓬勃发展，并出现了像 CodeRabbit、Greptile、Qodo 和 SonarQube（现在也包括 Gitar）等专门用于代码审查的工具。此外，编程环境本身也提供了诸如 Claude Code Review、Cursor Review 和 GitHub Copilot Review 等代码审查功能。还有一些之前不涉及代码审查但具有代码库上下文信息的工具也开始提供此服务，比如 Sentry 的 Seer AI 审查和 Linear 代码审查。

我们曾讨论过《如何利用 AI 进行软件开发》，这不仅限于 Uber：像 Cloudflare（AI 代码审查员）、Faire（Fairey）和 HubSpot（Sidekick）这样的公司，在发现内部实现比集成供应商效果更好的情况下，也开发了工具来优化其代码审查流程。

另一种方法是思考如何验证代码而不是进行审查。
这说起来容易做起来难；理论上，充分的测试应该能够验证代码是否按预期工作。但什么是“充分”的测试？我们要谈哪种类型的测试呢？是集成测试和端到端测试吗？还是模糊测试？或者是形式化的方法？我们怎样才能确保新添加的测试能正确地覆盖功能呢？如何将所有这些都与可观测性联系起来？

过多的代码审查正在耗尽工程师，导致质量不高的代码审查。

我经常听到一些开发者反映，其他人在没有真实反馈的情况下就批准了 AI 生成的代码审查结果。而那些依旧投入相同时间和精力进行代码审查的人则感到被大量无意义的 PR 压得喘不过气来。

这些问题确实存在，并且目前的解决方案更像是实验。
