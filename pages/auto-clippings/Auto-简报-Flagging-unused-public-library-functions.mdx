# Rust 社区技术情报简报：Workspace 级别未使用公共 API 检测探讨

### 💡 TL;DR
开发者在 Rust 工作空间（Workspace）架构下，面临无法自动检测和清理库（Library Crate）中未被其他成员实际调用的公共（`pub`）方法的困境，期望寻找一种跨 Crate 的静态代码检查方案，以解决原生工具默认忽略公共 API 死代码检查所带来的代码维护与腐化难题。

---

### 🔍 核心观点与技术细节

*   **Workspace 模块化架构实践**：作者采用 Rust Workspace 模式管理大型项目，将不同上下文（如数据清洗、模型训练、评估）拆分为独立的库（Library Crates），并配合一组执行常规任务的二进制文件（Binary Crates）。
*   **API 最小化暴露原则**：在良好的设计下，每个库仅向 Workspace 内部的其他部分导出 3 到 4 个关键函数或方法，以控制模块间的耦合度。
*   **Rust 原生 Lint 机制的局限**：Rust 编译器（`rustc`）和 `clippy` 的 `dead_code` 检查默认会忽略所有标记为 `pub` 的项。这是因为编译器假设公共 API 可能会被外部未知的 Crate 使用，从而无法在 Workspace 内部进行全局的死代码判定。
*   **缺乏跨 Crate 追踪方案**：作者尝试了搜索引擎和 AI 工具，均未找到能在 Workspace 级别跨 Crate 追踪 `pub` 方法调用链的有效方案；同时，通过手动将 `pub` 降级为私有（非 `pub`）来测试是否有人使用的“破坏性测试”方法在实际工程中不可行。

---

### 🎯 核心痛点提炼

1.  **跨 Crate 死代码检测能力缺失**
    Rust 原生工具链（如 `cargo` 和 `clippy`）缺乏在 Workspace 范围内进行全局上下文分析的能力。工具无法区分“被外部未知项目使用的公共 API”和“仅在当前 Workspace 内部使用但已无调用者的公共 API”，导致无法自动标记后者。
2.  **公共 API “僵尸化”与清理成本高昂**
    在大型项目的持续迭代中，库中极易积累大量实际上已无调用者的“僵尸”公共方法。由于缺乏自动化的清理工具，开发者只能通过人工审查或高风险的破坏性修改（如强行改为私有并观察编译报错）来发现它们，这极大地增加了代码重构和技术债务清理的成本。
