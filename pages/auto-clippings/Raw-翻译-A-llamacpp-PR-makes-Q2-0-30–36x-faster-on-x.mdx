【帖子标题】：A llama.cpp PR makes Q2_0 3.0–3.6x faster on x86 CPUs, 8B decode goes 2.39 → 8.20 tok/s

【帖子正文】：
我正在浏览当前的 llama.cpp CPU PRs，而 #26348 突然吸引了我的注意，因为这并不是普通的 +5% 内核优化。

它为 Q2_0 × Q8_0 点积添加了 x86 VNNI 实现，并且作者控制下的 CPU 仅基准测试显示，在从 1.7B 到 27B 的 Bonsai 模型中，吞吐量大约提高了3-3.6倍。

设置：
- AMD EPYC 9645
- 8 个 CPU 核心
- 仅 CPU
- GGML_NATIVE=ON
- OpenMP 启用
- BLAS 禁用
- -t 8 -ngl 0 -fa off
- 冷启动后运行3次
- group-64 Q2_0 Bonsai GGUF

结果：
1.7B
pp512: 14.07 → 50.47 tok/s (3.59倍)
tg128: 10.22 → 33.28 tok/s (3.26倍)

4B
pp512: 5.41 → 19.40 tok/s (3.59倍)
tg128: 4.45 → 13.36 tok/s (3.00倍)

8B
pp512: 2.82 → 10.26 tok/s (3.64倍)
tg128: 2.39 → 8.20 tok/s (3.43倍)

27B
pp128: 0.79 → 2.85 tok/s (3.59倍)
tg32: 0.72 → 2.37 tok/s (3.32倍)

27B 的基线竟然如此之慢，以至于 pp128 过程几乎用了近3分钟。

实际上发生的变化相当小：现有的 Q2_0 点积使用了 AVX-VNNI / AVX-512 VNNI 路径替代通用实现。

这种从参考 Prism 实现改编而来的内容也揭示了一个有趣的问题，即在正常消费者级的 Intel CPU 上表现不佳。

在一个 i5-13400 上，Q2_0 由于 12-14 代 Intel 处理器支持 AVX-VNNI 而不支持 AVX-512，因此悄无声息地丢失了快速路径。没有任何信息告诉用户这种情况发生了，看起来 Q2_0 极为缓慢。

他们对 i5-13400 进行了受控 A/B 测试：
Ternary-Bonsai-8B Q2_0
解码：2.17 → 6.92 tok/s
提示评估：2.7 → 8.6 tok/s

再次强调，使用 VNNI 路径大约有3.2倍的提升。

这里有一些重要的注意事项：
- 上游 llama.cpp PR 仍处于开放状态，尚未合并
- 这特指 Q2_0，并非为 Q4/Q5 等提供免费三倍加速
- 主要上游基准测试使用的是仅8个核心的 EPYC 处理器
- i5-13400 的结果来自 Prism 参考实现，而非 exact group-64 上游 PR
- 从融合乘加行为中存在细微数值差异

在正确性方面，作者报告了 14,000 次随机比较，在内核级别逐位匹配。在困惑度烟雾测试中，两种版本在选择相同最可能的下一个词上 99.216% ± 0.554%，KLD 差异非常小。

这种 llama.cpp 优化我更希望能在普通的消费者硬件上进行测试，而不是另一个服务器 CPU 上。

如果有 Alder/Raptor Lake 或 Zen 4/5 并且能编译 PR 分支的任何人，请发布你们在 llama-bench 的前后结果。尤其是对笔记本电脑感兴趣，3 倍加速在电源和内存带宽限制下是否会保持不变，或者在实际硬件中会大幅缩水？
