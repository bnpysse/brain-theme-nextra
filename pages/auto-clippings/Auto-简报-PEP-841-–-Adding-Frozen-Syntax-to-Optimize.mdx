### 📄 TL;DR（核心摘要）
PEP 841 提议引入 `f{}` 语法前缀以原生支持不可变集合与字典的字面量声明。通过将不可变性承诺直接嵌入语言语法层，Python 编译器可将此类表达式识别为编译期常量，直接折叠为单一 `LOAD_CONST` 字节码并固化至 `.pyc` 缓存中，从而彻底消除运行时的构造函数调用、动态类型推导与内存分配开销，实现类似内置可变字面量的高性能优化路径。

### 🔑 核心技术细节与观点
- **语法扩展**：新增 `f{元素, ...}` 格式化为 `frozenset`，`f{键: 值, ...}` 格式化为 `frozendict`，实现不可变容器的字面量级声明。
- **编译器范式升级**：打破当前“不可变性依赖运行时构造函数”的局限，将冻结对象提升至编译器优化管道的“头等公民”地位。
- **字节码折叠机制**：编译阶段直接解析为单一的 `LOAD_CONST` 操作码，跳过 `BUILD_SET`/`BUILD_MAP` 等运行时指令链。
- **持久化缓存策略**：由于类型与内容在编译期已完全确定，可直接序列化进 `.pyc` 文件，模块导入时无需重复计算哈希、验证不可变性或分配堆内存。
- **类型系统协同**：明确区分可变字面量（如 `[]`、`{}`）与不可变字面量的底层语义，便于静态分析工具与类型检查器进行更精确的流数据流追踪。

### 🎯 讨论的核心痛点
当前 Python 在不可变容器使用上存在**“语法表达与编译优化断裂”**的结构性矛盾：开发者虽频繁使用 `frozenset()` 或第三方 `frozendict` 追求不可变性与哈希安全，但底层仍需经过完整的运行时构造链路（函数调用 → 临时列表/元组转换 → 迭代计算哈希 → 动态对象分配）。这不仅导致高频初始化场景下的性能损耗与内存碎片，更使 CPython 编译器无法将此类表达式纳入常量折叠（Constant Folding）体系。本 PEP 直指这一瓶颈，试图通过“语法即不可变契约”的设计，打通从源码到 VM 的执行优化断层，填补 Python 在高性能不可变数据结构原生支持上的最后一块拼图。
