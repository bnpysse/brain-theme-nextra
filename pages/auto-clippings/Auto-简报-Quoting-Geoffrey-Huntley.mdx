# 精华简报：用 Pre-commit Hook 强制 AI 编码代理遵循架构规范

&gt; **来源**：Simon Willison 博客 · 引用 Geoffrey Huntley 的观点

&gt; **主题**：AI 编码代理（Coding Agents）的工程化治理

---

## 一、TL;DR（核心主旨）

Geoffrey Huntley 提出一个关键观点：当 AI 代理编写代码时，**文档（如 AGENTS.md）不足以约束其行为**——代理对文档的遵循是概率性的，且会随时间漂移。真正有效的做法是**在工程基础设施层面施加机械性强制**：编写 pre-commit hook 检查 git diff，一旦发现代理绕过诊断库直接调用可观测性模块，就**拒绝提交并注入一条提示**，告诉代理改用正确的库。结果是：合规率从"时好时坏"变成"十次十次达标"。这揭示了一个更深层的判断——**"没有人应该再手工敲代码了，剩下的工作是什么？"** 答案是：设计规则、构建护栏、治理代理行为。

---

## 二、核心观点与技术/商业洞察

### 1. 文档会漂移，机制不会

AGENTS.md 这类代理指令文档是**被动约束**——它依赖代理"读到并遵守"，而 LLM 的行为本质上是概率性的，即使读到了也可能不执行。更糟的是，代码库演进后文档会过时（drift），代理遵循的是一份"过期地图"。Huntley 的洞察是：**把约束从"文档层"下沉到"机制层"**，让 git hook 这种确定性基础设施来把关，彻底消除对代理自觉性的依赖。

### 2. "失败即教学"：将 CI 管道变成反馈回路

这个模式最精妙之处在于：当 commit 被拒绝时，**错误信息本身就是一次即时纠偏提示（injected prompt）**。代理看到失败 → 读取提示 → 修正行为 → 重新提交。这形成了一个闭环：

```

代理写代码 → git diff 检查 → 发现违规 → 提交失败 + 注入提示 → 代理自我修正 → 通过

```

这本质上是一种**工程化的强化学习信号**——不需要微调模型，不需要复杂的评估框架，只需要在 git 层面做一次模式匹配。它把"概率性的模型行为"转化为"确定性的工程结果"。

### 3. 治理点选在"边界"而非"过程"

Huntley 没有试图在代理运行过程中实时监控或干预（那需要深度集成特定代理工具），而是选择在 **git commit 这个所有代码必经的边界**上做检查。这个设计选择极具工程智慧：

- **与代理无关**：无论用的是 Claude Code、Cursor 还是其他工具，都无法绕过 git hook；

- **与语言无关**：检查的是 diff 中的调用模式，不依赖特定框架；

- **成本极低**：一次 diff 扫描，毫秒级完成，却获得了 100% 的覆盖率。

### 4. "十次十次达标"：从概率到确定性的跃迁

"All of a sudden it's ten out of ten"——这句话点出了 AI 工程化的核心命题：**LLM 的输出是概率性的，但工程系统需要确定性**。Huntley 的方法论意义在于：不要试图让模型变得更可靠（那是模型层的问题），而是**在系统边界上建立确定性检查，把不可靠的输出拦截在门外**。这是"信任但验证"（trust but verify）在 AI 时代的工程化落地。

### 5. "剩下的工作是什么？"——工程师角色的重新定义

"Nobody should type code by hand anymore. Here's what's left." 这句话是一个宣言：如果 AI 代理负责写代码，那么人类工程师的剩余价值在于：

- **定义架构约束与编码规范**（什么允许、什么禁止）；

- **构建治理机制**（hook、linter、CI 检查、运行时守卫）；

- **设计反馈回路**（让代理从失败中学习）；

- **裁决架构决策**（哪些抽象必须被强制遵循）。

换句话说，**工程师从"代码的生产者"转变为"代码生产的制度设计者"**。

## 三、对行业的启发与影响

### 1. "Agentic Engineering"正在成为独立学科

本文的标签中出现了 `agentic-engineering`——这标志着一种新的工程实践正在成形。它不同于"提示工程"（prompt engineering），也不同于传统的软件工程，而是**围绕 AI 代理构建治理系统**的学问：如何约束、引导、评估、纠偏代理行为。未来我们会看到更多这类模式被系统化、工具化。

### 2. 催生"代理治理"工具链

Huntley 的手写 hook 方案会迅速产品化。可以预见：

- **规则即代码**：声明式定义"代理必须/禁止做什么"，自动生成 git hook / CI 检查；

- **代理行为审计**：记录代理的每次违规与修正，形成行为画像；

- **策略分发**：企业级统一配置，确保所有开发者的代理遵循同一套架构规范。

### 3. 确定性护栏是 AI 代码落地的"安全网"

当前企业对 AI 编码最大的顾虑是"不可控"。Huntley 的方案提供了一个极具说服力的答案：**你不需要控制代理的每一个动作，只需要在关键边界上设置确定性检查**。这个思路可以推广到更多场景——依赖许可检查、安全漏洞扫描、API 滥用检测、机密信息泄露防护……凡是能写成 diff 规则或静态检查的约束，都可以从"提示代理遵守"升级为"强制代理遵守"。

### 4. 高级工程师的价值重心迁移

当 AI 能写大部分常规代码时，高级工程师的核心竞争力不再是"写得多快多好"，而是：

- **能否设计出代理无法绕过的架构约束**；

- **能否构建让代理自我纠错的反馈机制**；

- **能否定义出机器可执行的"架构意图"**。

这类似于从"运动员"到"裁判员+规则制定者"的角色转变。**架构师的新职责是：把架构决策编码为代理必须服从的物理定律。**

### 5. 对 AI 编码工具厂商的战略启示

Claude Code、Cursor、GitHub Copilot 等工具厂商应关注这一趋势：**代理的"可治理性"（governability）正在成为差异化竞争要素**。谁能提供更完善的治理接口——细粒度的行为钩子、可编程的约束机制、与 CI/CD 深度集成的反馈通道——谁就能赢得企业级客户。Huntley 的 hack 本质上是在弥补当前代理工具在治理能力上的缺失，这恰恰指明了产品演进的方向。

---

&gt; **一句话总结**：在 AI 代理编写代码的时代，**文档是建议，机制是法律**——把约束写进 git hook，让每一次违规提交都成为代理的一次"即时教学"，人类工程师的剩余价值在于设计这套治理系统，而非亲手写代码。
