【文章标题】：关于"解析而非验证"的Rust实践思考

【文章正文】：
Like many programmers, I find Alexis King's Parse, don't validate article fascinating, because it gives a name to an idiom that seems familiar and important - one I've observed and used in the past without naming it explicitly.
和许多程序员一样，我发现Alexis King的《解析，而非验证》一文令人着迷，因为它为一个看似熟悉且重要的编程范式赋予了名称——这个范式我过去曾观察和使用过，但从未明确命名过。

This post is a review of the "Parse, don't validate" pattern applied to the Rust programming language (the original post uses Haskell). I was particularly interested in finding educational examples of this pattern in the Rust standard library and other well-known projects.
本文是对"解析而非验证"模式在Rust编程语言中的应用回顾（原文使用Haskell）。我特别关注在Rust标准库和其他知名项目中寻找这个模式的教学示例。

Without repeating the original article (please read it first!), here's the gist of it.
在不重复原文内容的前提下（请先阅读原文！），以下是其核心思想。

Consider the venerable Vec; its first method returns Option&lt;&T&gt;. Why? Because a vector is not guaranteed to have any elements in it, so what to do if first is invoked on an empty one?
以经典的Vec为例：它的first方法返回Option&lt;&T&gt;。为什么？因为不能保证向量中包含任何元素，如果在空向量上调用first该怎么办？

Returning an Option in this case is idiomatic in Rust [1], with convenient syntax sugar for accepting the result of functions that return Option and deciding what to do next.
在这种情况下返回Option是Rust的惯用法[1]，它提供了方便的语法糖来处理返回Option的函数结果并决定后续操作。

So what's the issue?
那么问题出在哪里？

Imagine we have a function to read some configuration paths from an env var, while enforcing the invariant that the list can't be empty:
假设我们有一个从环境变量读取配置路径的函数，同时强制要求列表不能为空：

use anyhow::&#123;Result, ensure&#125;;
fn get_configuration_directories() -&gt; Result&lt;Vec&lt;PathBuf&gt;&gt; &#123;
    let value = env::var("CONFIG_DIRS").context("could not read CONFIG_DIRS")?;
    let directories: Vec&lt;PathBuf&gt; = value
        .split(',')
        .map(str::trim)
        .map(PathBuf::from)
        .collect();
    ensure!(!directories.is_empty(), "empty CONFIG_DIRS");
    Ok(directories)
&#125;

So far, so good. Now let's take a typical usage of this function:
目前看起来不错。现在来看这个函数的典型用法：

fn main() -&gt; Result&lt;()&gt; &#123;
    let config_dirs = get_configuration_directories()?;
    match config_dirs.first() &#123;
        Some(cache_dir) =&gt; initialize_cache(cache_dir),
        None =&gt; unreachable!("already checked that CONFIG_DIRS is non-empty"),
    &#125;
    Ok(())
&#125;

Once get_configuration_directories returns a successful result, we are guaranteed that the vector isn't empty. And yet, if we want to get the first element of this vector, we have to use the first method that returns Option&lt;&T&gt;.
当get_configuration_directories返回成功结果时，我们确信向量不为空。然而，如果我们想获取这个向量的第一个元素，仍然必须使用返回Option&lt;&T&gt;的first方法。

We are therefore forced - again - to handle a potentially empty case (where the option is None).
因此我们被迫——再次——处理可能为空的情况（即Option为None的情况）。

As the original article states, this has a number of problems with code clarity, potential performance implications and a ticking time bomb if the invariant is ever changed in get_configuration_directories.
正如原文所述，这会带来代码清晰度问题、潜在性能影响，并且如果get_configuration_directories中的不变量发生改变，就会成为定时炸弹。

The core issue is that Vec is fundamentally a type that can be empty; we can carry along a "This one can't be empty, pinky promise!" comment on all the relevant code, but it's not formally checked by anything.
核心问题在于Vec本质上是可以为空的类型；我们可以在所有相关代码中添加"这个不能为空，我保证！"的注释，但这没有任何形式化的检查。

A type for "non-empty" vector
"非空"向量的类型解决方案

The solution is leveraging the type system to enforce a newly established invariant. We can use a separate type for "a vector that cannot be empty"; in fact, such types already exist in several Rust crates - for example nonempty:
解决方案是利用类型系统来强制执行新建立的不变量。我们可以为"不能为空的向量"使用单独的类型；事实上，这样的类型已经存在于多个Rust crate中——例如nonempty：

pub struct NonEmpty&lt;T&gt; &#123;
    pub head: T,
    pub tail: Vec&lt;T&gt;,
&#125;

This type has no constructor that permits "no elements"; its new takes one element, and its first method returns &T without an Option:
这种类型没有允许"无元素"的构造函数；它的new方法接受一个元素，first方法直接返回&T而不需要Option：

pub const fn new(e: T) -&gt; Self &#123;
    Self::singleton(e)
&#125;
pub const fn singleton(head: T) -&gt; Self &#123;
    NonEmpty &#123;
        head,
        tail: Vec::new(),
    &#125;
&#125;
pub const fn first(&self) -&gt; &T &#123;
    &self.head
&#125;

The rest of the crate deals with making NonEmpty behave as close as possible to a normal Vec, by implementing many useful traits, as well as conversions like:
该crate的其他部分通过实现许多有用的特性以及转换方法，使NonEmpty的行为尽可能接近普通Vec：

pub fn from_vec(mut vec: Vec&lt;T&gt;) -&gt; Option&lt;NonEmpty&lt;T&gt;&gt; &#123;
    if vec.is_empty() &#123;
        None
    &#125; else &#123;
        let head = vec.remove(0);
        Some(NonEmpty &#123; head, tail: vec &#125;)
    &#125;
&#125;

Let's see how our get_configuration_directories function would look if it returned a NonEmpty instead of a plain Vec:
让我们看看如果get_configuration_directories函数返回NonEmpty而不是普通Vec会是什么样子：

fn get_configuration_directories() -&gt; Result&lt;NonEmpty&lt;PathBuf&gt;&gt; &#123;
    let value = env::var("CONFIG_DIRS").context("could not read CONFIG_DIRS")?;
    let directories = value
        .split(',')
        .map(str::trim)
        .map(PathBuf::from)
        .collect();
    let Some(directories) = NonEmpty::from_vec(directories) else &#123;
        bail!("CONFIG_DIRS cannot be empty");
    &#125;;
    Ok(directories)
&#125;

Note the use of NonEmpty::from_vec here - this is where the invariant is established. Now a successful result is NonEmpty, not just Vec. The client code looks like:
注意这里使用了NonEmpty::from_vec——这就是不变量建立的地方。现在成功的结果是NonEmpty，而不仅仅是Vec。客户端代码如下：

fn main() -&gt; Result&lt;()&gt; &#123;
    let config_dirs = get_configuration_directories()?;
    initialize_cache(config_dirs.first())?;
    Ok(())
&#125;

There's no need to check if the returned value is empty again; this is enforced by the type system!
不需要再次检查返回值是否为空；这由类型系统强制执行！

This is where the parse vs. validate terminology of the original article comes from. When get_configuration_directories returned a Vec, it simply validated it. But when it returns a NonEmpty - the vector is transformed into another entity which carries additional meaning.
这就是原文中"解析"与"验证"术语的来源。当get_configuration_directories返回Vec时，它只是进行了验证。但当它返回NonEmpty时——向量被转换为具有附加含义的另一种实体。

If we treat the concept of parsing in the most generic sense - "transforming data from one format to another", this fits.
如果我们以最通用的方式理解"解析"的概念——"将数据从一种格式转换为另一种格式"，这就很贴切。
