### 📝 TL;DR（一句话摘要）
Rust 标准库中的 `format!()` 宏在初始化输出字符串时，并非基于实际内容长度进行精确分配，而是依赖仅统计格式模板中字面量的启发式估算；该机制既不保证容量上限也不保证下限，极易在运行时触发额外扩容，从而在性能敏感场景中造成隐蔽的内存分配抖动与性能损耗，且该行为自 2017 年起已成为官方设计的既定事实。

### 🔍 核心观点与技术细节
- **容量估算机制透明化**：底层实现通过遍历格式字符串的字面量字符数生成初始 `capacity`，完全忽略 `{}` 占位符及其对应参数的运行时大小。
- **无严格上下界保障**：估算值仅为经验性参考，实际写入时常发现预估容量不足，直接触发标准库的倍增式扩容逻辑（通常为 2x 策略）。
- **运行时长度不参与预分配**：由于格式化参数属于运行时动态数据，编译器无法在栈帧初始化阶段获知其大小，故设计为“先盲估、后动态扩容”。
- **历史演进与决策背景**：该行为源于 2017 年合并的 PR #39356，当时团队为平衡编译期开销与通用场景下的平均性能，选择了轻量级静态估算方案。
- **开发者认知偏差**：多数 Rust 用户默认认为常用内置宏具备“自适应预分配”能力，实际上长期存在误判，需在实际调优中重新审视该类代码路径。

### ⚠️ 核心痛点提炼
**隐性内存分配抖动导致的性能优化盲区**。`format!()` 作为 Rust 生态中使用频率最高的字符串构造原语，其底层采用的“静态字面量估算 + 动态二次分配”策略缺乏运行时可见性，使开发者在高吞吐、低延迟或资源受限（如嵌入式/游戏热路径）场景中，极易因盲目信任宏的行为而引入难以定位的 realloc 风暴，违背了 Rust 在零成本抽象层面提供的确定性预期。建议在关键性能路径中显式使用 `String::with_capacity()` 配合已知上限，或采用 `write!()`/`formatter` 接口接管缓冲区生命周期。
