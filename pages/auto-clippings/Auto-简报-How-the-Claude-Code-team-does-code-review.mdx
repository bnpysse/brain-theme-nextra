# 精华简报：Claude Code 团队如何做代码审查

## 一句话核心

当 AI 生成代码的规模远超人工逐行审查能力时，Claude Code 团队将代码审查从“人类读代码”重构为“用自动化检查捕捉风险，用最少人类注意力守住底线”，在不增加回滚和事故率的前提下，实现了 PR 数量翻倍、回滚率下降 40% 以上。

## 背景与挑战

- Claude 编写了 Claude Code 自身约 90% 的代码，变更量急剧膨胀：

- Anthropic monorepo 每日落地变更从 5 月的约 2,500 个增至 9 月的 30,000+ 个。

- Claude Code 独立仓库同样承受巨大压力。

- 传统人工逐行审查在如此速度下“几乎不可能”。

## 核心理念转变

- 旧问题：“有没有人读过代码？” → 新问题：“这个变更可能出什么问题？哪种检查（自动化还是人工）最适合发现它？”

- 审查不再是 PR 合并前的“终点关卡”，而是像“写作时的拼写检查”一样持续进行。

- 大多数变更在人类介入前，已被 Claude 至少审查和修复过一轮。

## 关键策略

1. **机器承担大部分阅读，人类只做机器做不了的事**

- 保留人类注意力用于更高层次的判断和新型问题。

- 优化目标：大多数 PR 合并时最多只有一个人参与（可以是作者本人），且不增加回滚/事故率。

2. **用指标衡量真实成本**

- 人类时间 = 审查时间 + 修复坏代码的时间，两者必须同时优化。

- 跟踪指标：每个 PR 的人工审批数（中位数和 95 分位）、人工评论数、PR 等待人的时长。

- 护栏指标：回滚率、事故率——如果上升，说明只是把时间从“审查”挪到了“救火”。

3. **审查前置到 PR 创建之前**

- 给 Claude 可运行的验证方式（测试、构建、截图对比设计稿），要求它展示输出而不是说“完成了”。

- 用子代理（subagent）以全新上下文审查 diff。

- 团队内部技能（skills）：一个找 bug、一个简化 diff、一个做端到端行为检查；UI 变更还对照设计规范检查。

4. **验证是效果倍增器**

- Claude Code 创始人 Boris Cherny 认为，给 Claude 验证其工作的方法，是获得好结果“最重要的事”，效果提升 2–3 倍。

- 验证方式因领域而异：bash 命令、测试套件、浏览器/手机模拟器测试等。

5. **从源头修复重复问题**

- 当自动化审查反复标记同一类问题时，直接修复源头：

- 更新 skill

- 增加 lint 规则

- 更新指令文件

## 指令文件设计（可借鉴的实践）

- **CLAUDE.md**：告诉 Claude 项目是什么——技术栈、约定、目标和非目标。保持简短，指向其他文档；审查者会标记违反约定或使文档过时的变更。

- **REVIEW.md**：由代码所有者编写，告诉审查者该部分代码中什么最重要。优秀范例的特征：

- 简短

- 明确“失败长什么样”（文档是“它撒谎”，配置是“它路由错误”）

- 限制吹毛求疵的数量

- 列出可跳过的路径

- 要求提供文件和行号作为证据，而非猜测

- 要求摘要以计数开头，并直说改了什么、为什么

## 数据成果

- 6 月至 9 月：合并 PR 数量翻倍以上，回滚比例下降超过 40%。

## 启示

- 代码审查的第二项工作（知识传递、团队共识、作者成长）依然存在，文章虽主要聚焦“发现问题”，但暗示并未放弃。

- 核心方法论可迁移：**不要追求“人读过代码”，而是系统性地回答“什么可能出错，谁最适合抓住它”**；用自动化覆盖常规错误，把人类注意力留给真正需要判断力的地方，同时让撤销错误变得快速、廉价。
