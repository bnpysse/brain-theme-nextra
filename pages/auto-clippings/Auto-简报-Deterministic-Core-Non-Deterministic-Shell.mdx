### 精华简报：确定性核心与非确定性外壳架构解析

#### 核心概念
Gary Bernhardt提出的"功能性核心，命令式外壳"架构（2010年）演进为更普适的"确定性核心，非确定性外壳"模式。该架构将系统划分为：
- **确定性核心**：具有严格数学确定性（相同输入→相同输出），包含核心业务逻辑
- **非确定性外壳**：处理所有外部交互（IO、状态管理等），允许非确定性行为

#### 架构对比
| 维度                | 确定性核心                          | 非确定性外壳                    |
|---------------------|-----------------------------------|-------------------------------|
| 主要职责            | 业务决策                          | 依赖协调                      |
| 执行特征            | 多分支路径                        | 线性流程                      |
| 外部交互            | 完全隔离                          | 集成所有IO操作                |
| 测试友好度          | 无需mock，完全可复现              | 需模拟外部环境                |
| 代码示例            | 纯函数/状态机                     | 数据库/网络操作               |

#### 关键演进
1. **从函数式到确定性**：突破纯函数限制，承认状态机等命令式实现也可具备确定性
2. **确定性判定标准**：任何给定输入序列能产生确定输出序列的实现方式
3. **典型非确定性操作**：
   - 未 seeded 的随机数
   - 异步/并发操作
   - 所有IO操作（网络、存储、IPC等）

#### 工程实践价值
1. **测试优势**：
   - 核心逻辑测试覆盖率可达100%
   - 消除flaky tests（非确定性测试失败）
   - 测试即文档（完全可复现的业务规则）

2. **架构解耦**：
   - 通过"依赖倒置"将非确定性操作推到系统边缘
   - 核心代码不直接调用new Date()等非确定性方法

3. **遗留系统改造**：
   - 识别现有代码中的"隐性核心"（天然确定性片段）
   - 通过"strangler pattern"逐步抽离核心逻辑
   - 案例：FoundationDB通过严格分层实现极致确定性

#### 实施建议
```javascript
// Bad: 非确定性侵入核心
function calculateDiscount(userId) {
  const user = db.queryUser(userId); // IO操作
  return user.vip ? 0.2 : 0.1; 
}

// Good: 确定性核心
function calculateDiscount(isVip) { // 参数化输入
  return isVip ? 0.2 : 0.1;
}

// Shell处理IO后调用核心
async function getDiscount(userId) {
  const user = await db.queryUser(userId);
  return calculateDiscount(user.vip); 
}
```

#### 行业启示
1. 在AI时代，确定性核心架构对LLM生成代码的可靠性验证尤为重要
2. 与"微服务架构"的协同：将非确定性操作集中在边界服务
3. 性能权衡：某些场景（如游戏开发）需在确定性与非确定性间取得平衡

该模式为处理复杂系统提供了可测试性、可维护性和演进灵活性的三角平衡，是应对现代软件复杂性的有效思维框架。
