### 💡 TL;DR
本帖作者将长期在项目复用的“恐慌安全型锁处理逻辑”封装为独立 Rust crate（`poisoned`）。该工具通过提供 `LockExt` trait 及 `or_panic()` 方法，专门用于处理 `Mutex`/`RwLock` 被污染时的解锁行为：在当前线程已处于 panic 状态时，自动调用 `PoisonError::into_inner()` 安全回收锁守卫以阻断二次恐慌；在非 panic 状态下则严格遵循 Rust 标准库的污染拦截策略。该实现零依赖、单 Trait 设计，有效降低了并发资源管理中的边缘崩溃风险与重复造轮子成本。

### ⚙️ 核心技术细节
- **扩展接口设计**：定义单一 `LockExt` trait，不侵入原有同步原语体系，采用组合式调用风格（如 `cache.lock().or_panic()`）。
- **恐慌状态感知**：底层借助 `std::thread::panicking()` 进行运行时状态嗅探，精准区分“常规访问”与“栈回退上下文”。
- **双模行为控制**：
  - `or_panic()`：panic 中静默解包并返回内部值；正常态下遇污染锁依旧 panic。
  - `or_panic_with()`：支持闭包延迟构造诊断信息，便于生产环境日志追踪。
- **工程属性**：纯标准库实现、无第三方依赖、内存与编译开销极低，符合 Rust 生态对工具crate “小而美” 的设计哲学。
- **使用边界**：主要适用于 `Drop` 实现、背景任务守护线程及需要保证最终一致性的资源清理场景。

### 🎯 讨论的核心痛点
**隐蔽性极高的“二次恐慌”（Double Panic）陷阱**  
在 Rust 并发模型中，当某线程恐慌导致共享锁变为 `poisoned` 状态后，若后续析构逻辑（尤其是自定义类型的 `Drop` 方法）恰好尝试对该锁执行 `.lock()`/`.read()`，会因未处理的 `PoisonError` 再次触发 panic。根据 Rust 运行时规则，二次恐慌将直接 abort 进程而非优雅回退。该缺陷极具欺骗性：仅在“特定线程路径 + 污染锁接触 + 触发 Drop”的罕见交集下显现，传统单元测试极难覆盖，迫使开发者反复手写条件判断与 `into_inner()` 防护逻辑。`poisoned` crate 的出现正是为了将这套高频试错经验产品化，填补标准库在“恐慌期资源安全释放”层面的自动化空白。
