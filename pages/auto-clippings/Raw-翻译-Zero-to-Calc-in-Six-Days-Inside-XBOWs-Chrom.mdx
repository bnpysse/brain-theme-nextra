Background: V8 and Renderer Sandboxes

V8 first contains JavaScript-engine corruption inside an in-process sandbox. Most JavaScript heap objects live in a reserved 4 GiB region, and many pointers are represented as offsets within that region. References to native objects and executable code receive additional protection. A V8 memory corruption bug can therefore give an attacker extensive control inside the cage without immediately yielding native code execution. V8 describes this design in The V8 sandbox.

Chrome then contains the renderer itself inside an operating-system process sandbox. Even an attacker with native code execution in the renderer cannot freely access the rest of the machine. Chromium's sandbox design document describes this outer boundary.

背景：V8和渲染器沙箱

V8首先将JavaScript引擎的破坏限制在进程内沙箱中。大多数JavaScript堆对象位于一个预留的4 GiB区域中，许多指针被表示为该区域内的偏移量。对原生对象和可执行代码的引用受到额外保护。因此，一个V8内存破坏漏洞可以让攻击者在笼子内部获得广泛的控制权，而不会立即获得原生代码执行能力。V8在其《V8沙箱》文档中描述了这一设计。

Chrome随后将渲染器本身包含在操作系统进程沙箱中。即使攻击者在渲染器中获得了原生代码执行能力，也无法自由访问机器的其余部分。Chromium的沙箱设计文档描述了这一外层边界。

The animated-WebP stage was a V8 sandbox escape, but rather than attacking the sandbox itself we exploited a property that the V8 sandbox deliberately does not enforce and that Blink incorrectly assumed it could trust. Finally, the exploit used an overflow in Crashpad to cross the final the outer process boundary and achieve unsandboxed code execution on the host.

Stage 1: Mutating the Immutable

The first vulnerability was in Maglev, V8's mid-tier optimizing compiler. To understand it, we need to look at deoptimization.

Optimized code operates under assumptions about the values and objects it handles. When an assumption stops being true at runtime, V8 must reconstruct ordinary JavaScript objects and continue in less specialized code. Some of those objects never existed in memory while the optimized code was running; the compiler had represented them only as values. Deoptimization must materialize them.
