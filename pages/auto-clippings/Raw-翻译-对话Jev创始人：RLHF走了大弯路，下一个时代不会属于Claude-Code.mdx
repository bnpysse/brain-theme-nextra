【文章标题】：对话Jev创始人：RLHF走了大弯路，下一个时代不会属于Claude Code

【文章正文】：

本文来自微信公众号：

Z Finance

，作者：ZF编辑部，题图来自：视觉中国

在 OpenAI 工作时，Diogo Almeida 经常感到困惑：为什么大家都在讨论如何让 ChatGPT 对开发者更有用，却很少追问，聊天模型本身是否适合成为软件的底层组件？开发者想控制一次工具调用，往往只能把要求写进提示词，再等待模型配合。在他看来，这套接口距离软件工程所要求的可控、可测与可组合，还有很远。

如今，作为 Typesafe 的 CEO，Almeida 正在用新模型 Jev 回答这个问题。他希望让软件直接调用智能，获得可以参与程序运行的决策、概率和评分。这场访谈围绕一个核心问题展开：

当智能足够便宜、足够快，也足够可靠，软件会发生怎样的变化？

从训练数据到 Agent 架构，他的判断都指向同一个方向——

AI 的巨大增量，可能藏在那些用户看不见、却每天运行无数次的软件流程里。

以下是他的主要观点：

AI 的下一种重要形态，是供程序调用的智能。

聊天模型主要围绕文本交互优化，而软件需要语义明确、行为可测的接口。Jev 尝试直接提供选择、概率与评分，让智能进入程序的条件判断、排序和执行流程。

模型是否可靠，不能只看回答是否正确，还要看它能否准确表达不确定性。

在 Almeida 看来，一个看似自信的答案不足以支撑生产系统；开发者需要能够据此设置阈值，决定何时自动执行、调用更强模型，或交给人工处理。他也承认，Jev 的校准与可靠性仍有明显改进空间。

更好的 AI 软件，需要把复杂任务拆成可以逐项验证的小决策。

与其让一个模型阅读庞大的系统提示词、一次性决定所有事情，不如将任务拆解，由代码组织流程、约束权限，并为每个判断建立测试。这样，修复一个问题才能成为可以持续验证的工程改进。

真正稀缺的能力，是为模型找到正确的训练目标。

他认为，行业过度关注算力与架构，却低估了任务定义和数据的作用。Typesafe 提出的 RLCD，即“校准决策强化学习”，就是尝试围绕模型参与程序运行这一目标，重新组织训练。

直接使用用户数据训练，可能让模型过拟合今天。

用户请求集中于少数高频场景，而他希望模型能支撑未来尚未出现的软件。因此，数据工作的重点是系统性寻找能力缺陷、补齐边缘情况，而非单纯积累更多真实请求。

智能变便宜之后，软件的设计方式也会改变。

当一次判断的成本与延迟足够低，开发者才可能在一次复杂推理周围安排数十次细小判断，用于验证、路由和检查。过去因成本过高而无人处理的企业数据，以及需要实时响应的应用，也可能因此获得新的使用空间。

今天的 Coding Agent 架构，受到 KV Cache 的深刻影响。

为了复用缓存，系统倾向于不断追加上下文，这又限制了任务分解、状态管理与多 Agent 协作。他期待开发者重新思考上下文如何检索、状态如何共享，让 Agent 更充分地采用成熟的软件工程方法。

AI 的发展路线仍然开放，前沿实验室当前的选择并不代表全部可能。

他质疑把持续加码推理强化学习视为唯一方向，也主张区分面向用户的产品约束与底层模型能力。这些判断背后的共同立场是：行业仍有大量尚未被充分探索的智能形态，值得围绕实际用途重新设计。

Jev发布周与AI经济革命

主持人：这周是个特别的日子，我的好友Diogo发布了Jev，相关内容已经刷屏各大平台的信息流时间线。你现在感受如何？此刻是怎样的状态？

Diogo Almeida：情绪层面？糟得不能再糟。我现在整个人心力交瘁，事情铺天盖地涌过来。我是一名技术出身的首席执行官，有一大堆紧急问题要处理。但从理性层面来讲——我在自己的线下沙龙活动里已经讲了很多年这个观点：整个AI行业就如同嘉年华里的镜子迷宫，所有人都有些狂热，说着各种匪夷所思、逻辑不通的言论。但就在这周，我感觉自己更加贴合现实了。大家终于意识到，AI的潜力远比过去人们设想的要大得多。没错，一场以AI为基础的经济革命重新具备实现的可能性。这实在太振奋人心了，开发者们看懂了，我非常激动。没错。我发自内心地感谢开发者群体，对整个社区满怀热忱。

主持人：太棒了。你昨天提到，你决定优先举办线上公开交流会，而不是接待一众VIP投资人，希望把最多的注意力留给工程师、开发者，是这样对吧？

Diogo Almeida：没错。有时候我会想，我正在和一众大人物对话，具体是谁我不便透露。我这个人或许太过直率坦诚，如果满满当当的日程表里排满各路要人，却没有留给社区的位置，我心里会很别扭。理想状态下，我希望把绝大多数时间留给社区。我甚至突发奇想过，要不要一边走到你的演播室，一边开线上交流会，但想想还是算了，实在太过疯狂。

主持人：确实。你们一直在Discord

（海外社群平台）

举办线上交流会，社群现在已经有十万成员。你的Twitter也彻底爆火。说个趣事，在AIE活动现场，你嘴上说着“大家可以关注我”，结果连自己的账号ID都没报出来。但这反而形成一种很有意思的个人特质：你不太懂得自我营销。

Diogo Almeida：我发推文感慨“好家伙，我们三条话题全都冲上热搜了”，结果有人当场点破我：那只是你的个人信息流而已。

主持人：也难怪你会这么感慨，毕竟这就是你亲手做出来的成果。恭喜你们取得的一切。后续有更多细节我们可以再聊。给那些不了解情况的听众做一个权威科普：Jev到底是什么？

Diogo Almeida：让我想想，这个问题并不好回答。

主持人：没关系，如果你需要思考，我可以稍后再问一遍。

Diogo Almeida：不用，我很乐意聊聊。说到这个问题，让我松一口气的一件事是：现在我不用再跟我父母解释它是什么了，ChatGPT可以替我解释。在我看来，我们需要一类全新的模型。我们并没有执着于给这一类模型起名字，我们想到最贴切的叫法是系统一号模型。之所以不叫决策模型，是因为系统一号模型的能力范畴不止于此，这点我只能说到这里。我们原本没料到这次会是一场大规模正式发布，我们手里还储备着不少技术成果。

主持人：你们本可以对外说这只是低调的研究预览版。

Diogo Almeida：某种程度上它确实算是。我们定义这类模型为：机器原生、系统一号、大型可编程模型。这类模型的目标是让代码成为模型的消费方。这和预训练大语言模型不一样，预训练大语言模型目标是做互联网文本自动补全；也和RLHF

（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习）

对话指令跟随模型不同，后者目标是输出文本回复。还有RLVR

（Reinforcement Learning with Verifiable Rewards，基于可验证奖励的强化学习）

，它和RLHF处于一个比较模糊的交界地带。而我们的模型输出会直接被代码调用，这也是Type‑Safe这个名字的由来。我们真正追求的是把AI的能力拉到尽可能强，实现这一点的方式就是把AI和软件深度结合。从对外接口到模型深层内部，我们所有设计都面向软件场景做优化。

第一点，Jev是我们第一款大型可编程模型，也可以叫系统一号模型，看你习惯怎么称呼。Jev的设计目标是intelligence per dollar

（每美元成本对应的智能能力）

，命名灵感来自Jevons paradox

（杰文斯悖论）

。我经常和别人争论，可靠性、成本、校准能力、速度，到底哪一项最重要。Jev作为系列模型，定位就是在每美元智能能力这条赛道上站在技术前沿。机器学习本身充满取舍权衡，如果你懂机器学习就会明白这一点，而我们正在全力朝着这个方向推进。

主持人：对我来说，校准是一个过去大家讨论度并不高的概念。我们之前做过一期节目，嘉宾是Hugging Face的Clementine Fourier。当时聊到一个观点：

经过RLHF处理后的模型，会发生mode collapsing

（模式坍缩）

，倾向于输出人类最想听到、概率最高的回答，而不是输出模型自身真实的确信判断。

RLHF、模式坍缩、校准与杨立昆

Diogo Almeida：我能不能就此展开说一说？我听说咱们听众技术水平普遍很高，我想深入聊这个话题。我们制作发布视频的时候，花了极大精力保证所有内容准确真实，而这在行业里其实并不常见。有一点几乎没人关注，就是RLHF带来的弊端，尤其是mode dropping

（等同于mode collapsing）

。我之后打算写一篇博客详细阐述，但我希望尽可能多的人了解这件事，这是一个很值得探讨的现象。

说一个比较尖锐的观点：我十分认同杨立昆

（AI科学家）

的很多观点，他的不少判断是准确度很高的。但他有一张非常出名、也饱受争议的幻灯片，标题大意是“大语言模型注定存在局限”。那张幻灯片有一个饼图，有一小块内容表达：随着sequence length

（序列长度）增

加，模型出错的概率会趋向升高。这个观点从数学推导上看似成立，但现实实验并不支持这个结论。这就是我很喜欢拿来科普的一类现象：理论推导看似没问题，但现实实证结果并不相符。

主持人：那造成这种矛盾的根源是什么？

Diogo Almeida：模式坍缩和这个问题是相关的。矛盾的根源在于：如果模型处于模式覆盖、分布校准的状态，它不会对异常输出施加过重惩罚。会有一部分输出属于分布外，一部分属于分布内，这就是完整覆盖数据分布的模型的表现。就像GAN

（Generative Adversarial Network，生成对抗网络）

诞生之前，生成模型输出的图像都是模糊的。而GAN会发生模式丢弃，直接抛弃少数类别，只生成高频常见样本，这就是上面那个理论预测没有成真的原因。

模型想要生成长文本还不出错，就要变得极度保守。错误发生的时候很容易被察觉到，但一些看似正确的细微偏差很难被发现。而校准问题会严重破坏字符串输出的概率分布。这是一个比较微妙的观点。这也是为什么字符串类模型并不擅长做决策，强行把字符串模型用于决策任务，效果会很糟糕。

主持人：说到GAN，那你是否认同杨立昆提出的解决方案，也就是世界模型，类似JEPA

（Joint Embedding Predictive Architecture，联合嵌入预测架构）

这类嵌入架构？问题根源在于模型基于token输出做推理，反复迭代拼接直到句子结束。JEPA 就是他给出的解法，也就是联合嵌入预测架构。你怎么看待这套方案？

Diogo Almeida：说实话我不太适合深入聊机器学习内部细节，但我的立场偏向实用主义。我怎么看待scaling laws

（缩放定律）

？要分情况看待。缩放定律告诉你投入多少资源性能会提升多少，但它往往意味着投入指数级资源，换来次线性的性能增益。除非增益本身价值极高，否则这笔投资并不划算。对我来说核心是：立足现有的条件，做出尽可能巨大的实际改变。

主持人：没问题，本期面向成年听众，不限制这类表达。我们后面也可以专门聊缩放定律。

Diogo Almeida：我们可以聊，但如果现在相关性不强，我想聊聊我踩过最惨痛的教训，这个话题会更切题。我对JEPA这套研究很欣赏，是很棒的早期研究。但它现阶段能不能落地实用？我不便过多评价。

可编程AI、拒绝输出与安全对齐

Diogo Almeida：现在AI研究领域有大量尚未打磨成型的宝藏思路，只是人们还没有找到合适的任务范式把它们发挥出来。我们这次发布，不光会推动公司自身发展，更会带动可编程AI这个方向整体向前。会有一波围绕我们的创业热潮，软件领域本身就具备巨大潜力。同时也会出现一批平行方向，探索各种可以增强软件能力的技术路径，开发者可以借此打造更厉害的作品。仿佛回到早期互联网那种充满活力的时代。也正是这个原因，Twitter上到处都在讨论Jev。

主持人：这和我们过去的固有认知截然不同，过去大家总觉得：缩放定律才是王道，只有大型实验室才有资格做这件事。

Diogo Almeida：允许我稍微跑个题，你或许会感兴趣，我们已经扯了好几个话题了。

主持人：我自己经常聊着聊着就跑题，听众需要自己梳理逻辑，但他们可以理解。

Diogo Almeida：Discord社群上很多人一直在问我一个问题，我还没有腾出时间详细解释：为什么我反对当下流行的安全对齐，为什么我们的模型不会输出拒绝回复。我并不反对安全这个理念本身，

但当下的安全对齐机制很多时候和用户真实需求相背离

。模型拒绝输出本质上属于一种类型错误。想象你在写代码调试，模型突然回复“抱歉，我无法读取DNA.py文件”，这会非常恼人。但大家已经被迫习惯这件事，近乎一种斯德哥尔摩综合征。

这里我又要引申一层思考：如果后台运行的一个依赖组件突然拒绝执行怎么办？别的开发者调用这个依赖，根本不知道内部发生了什么。你总不希望软件仅仅因为用户传入一段特殊输入就随机崩溃。这完全是不可理喻。

会出现这种问题，根源在于制定这套机制的人并不懂软件、不懂编程，执着于把AI做成AI协作者，而不去释放AI全部的原生能力。

主持人：说得有道理。你想要的是一个可以在各类场景通用的核心底层内核。

Diogo Almeida：完全正确，也就是认知内核。它要足够通用，适配各类使用场景，能够应对未来千奇百怪的业务需求。我们训练数据并没有覆盖所有这些稀奇场景，但模型依然可以正常工作，这不奇怪，我们训练素材本身就包含大量更奇特的案例。

回到安全对齐这个话题。在我看来，安全对齐对于ChatGPT、Claude这类面向聊天的产品是合理的。要区分能力对齐和安全对齐：能力对齐的目标是完成用户想要实现的事，这对于软件工程师至关重要。工程师希望工具按预期工作，可预测性越强，测试调试的工作量就越小。Jev距离这个目标还有很大差距。未来我们希望它的可靠性提升到数据库查询那样，几乎不用额外思考，需要intelligence的时候直接调用。

而安全对齐和指令跟随恰恰相反：它要求模型遵循第三方的约束，就像OpenAI做的那样。作为面向终端用户的聊天产品，这么做无可厚非。比如产品方不希望模型生成不适合公开场景的角色扮演内容，照顾到家庭用户，这完全可以理解。但放在API

（Application‑Programming‑Interface，应用程序编程接口）

接口层面就不合理。开发者需要围绕接口行为编写代码，安全对齐会严重损害开发者的使用体验。我尽量让自己保持冷静。

主持人：我理解你的观点，但我要提出一点反驳：如果有人拿它来造成人员伤亡该怎么办？色情、隐私问题尚且另说，但用于战争伤害人类，企业完全有理由限制API被用于这类场景。

Diogo Almeida：我理解这种现实层面的考量。但通用基础技术本身，不该承担这类价值判断。我个人当然不希望我们的技术被用来伤害人，希望它被用于造福世界。我会在产品业务层面施加引导，但绝不会在技术底层做这件事。在技术层做约束会破坏模型的通用智能。每一次为了适配特殊约束，都会让模型的智能能力进一步受损。现在很多大模型已经被破坏得相当严重。

在我看来，智能更应该像数据库。数据库不会去校验调用它的人拿它做善事还是恶事。还有一件很奇怪的事：有人在Slack上联系我们，问“我们能不能部署你们的服务”。我的想法是：我们对外提供的是API，你是开发者，这件事不该由我来评判。你甚至不需要完整知晓上层业务，任务会被拆解成细碎单元。我们不该获知下游使用者的全部意图，这才是给软件工程师最大自由度的合理边界。我们当然希望大家用它做有益的事，未来也会考虑开源、公益相关工作。但只要由我主导，就不会在技术底层植入这类价值偏向。

主持人：说得很好。顺着这个话题，简单澄清下你们之前引发一些误解的隐私、服务条款。请你用两句话说明，你们的API并没有设置严苛限制，你们很认真看待平台责任。

Diogo Almeida：我不清楚你具体指哪件事，但我看到不少关于基准测试的讨论。我们当然不会阻止别人做基准测试，说话我需要谨慎一点。

主持人：这件事你是公开发过声的。那是预览阶段的说法，正式发布已经取消该限制。不过团队有些动作我本人也不完全知情。

Diogo Almeida：很高兴知道团队对外传递了这个信息。我们咨询过法务。我们绝对不会阻止外界做基准测试。我非常反感公开基准测试，但适度使用私有代理基准测试我可以接受。公开基准最大的问题就是极易被刷分、被针对优化。不只是我们，假设两年之后行业涌现一大批同类竞品。我们售卖的核心是单位成本下的智能能力。

大家总在讨论成本、速度，这些固然重要，但最核心的是智能本身。成本和速度是你为之付出的代价，智能才是价值本源。
