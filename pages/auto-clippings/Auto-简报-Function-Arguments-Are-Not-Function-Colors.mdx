# 精华简报：函数参数为何不是函数颜色

**来源**：Hacker News Top  
**标题**：Function Arguments Are Not Function Colors  
**作者**：Jerf（jerf.org）  
**链接**：https://jerf.org/iri/post/2026/func_args_are_not_colors/

---

## 一、核心议题

在编程语言设计中，“函数颜色”（function colors）通常指 `async/await` 这类会“污染”调用链的特性：一个异步函数往往只能被另一个异步函数调用，否则必须显式处理边界。有人认为，像 Go 的 `context.Context` 这样的函数参数，一旦引入也会迫使所有相关调用者传递该参数，因此也构成一种“颜色”。本文作者反驳了这一观点，并提出一个可操作的判别标准：**看一项变化是否强制贯穿整条调用栈，还是可以在中间层被封装阻断**。

## 二、主要论点与论证

### 1. 表面相似：`context.Context` 似乎像颜色

在 Go 中，`context.Context` 通常被设计为贯穿多个函数传递，即使中间函数不直接使用它，也可能需要继续向下透传。一旦某个函数需要 context，所有可能用到它的下游调用者似乎都被“染色”了。由此，有人推而广之，认为所有函数参数都可以被视为一种“颜色”。

### 2. 关键反驳：如果参数是颜色，这个概念早已存在

作者的第一个反驳简明而有力：如果任何函数参数都是颜色，那么“函数颜色”这个概念不会在编程语言函数发明 50 多年后才被提出。这说明 `async` 等特性在语言中确实有某种独特之处，值得单独定义，而不能与普通参数混淆。

### 3. 判据：变化在调用图上的传播形状

作者提出一个思想实验：假设需要修改调用栈深层某个函数的属性——例如新增参数、改为异步、加入汇编等。这种修改对上层调用者的影响有三种情况：

- 不需要修改任何调用者；
- 可能需要修改直接调用者；
- 可能需要修改调用栈中的所有函数。

普通函数参数的变化，传播关系是**链式**的：每层调用者可以自行决定是否继续向上传播，也可以在任意一层“截断”变化，将其封装起来，使更上层完全无感知。  
而真正“颜色”的变化，传播关系是**全栈感染式**的：底层函数变色后，其上层所有函数立刻、不可避免地都要做出反应，无法在中间层局部封装。

### 4. 真实世界中的变化隔离

作者强调，正常参数变化虽然理论上可能一路传到 `main`，但这只是最坏情况，不是常见情况。实际上，结构化编程的核心价值正是隔离变化：上层函数不必知道底层函数的每个细节。如果每个参数变化都强制贯穿整条调用栈，那将是灾难性的，现实中并不会发生。

以 Go 的 `context.Context` 为例：任何一个普通函数都可以通过调用 `context.Background()` 获得一个合法但“空白”的 context。因此，当某个函数被修改为接受 context 时，不关心 context 的调用者只需简单传入 `context.Background()` 即可完成适配。这种“链条”在实际代码中往往在很早就被截断，而不是一路传到顶层。作者以自己的编码经验证实：在测试代码或其他不关心上下文的调用处，这种适配非常常见。

人们之所以会高估参数变更的传播成本，是因为“不得不一路改到 main”的情况虽然罕见，却在记忆中非常突出，容易被过度放大。实际上，这类事件频率很低，远不是常态。

## 三、关键洞察

文章的核心判别标准可以概括为：

- **普通参数**：变化可以被局部封装，中间层有权选择是否向上传播；
- **函数颜色**：变化无法被中间层封装，必须贯穿整个调用链。

换句话说，颜色的本质不是“需要传递某个东西”，而是**失去了在中间层隔离变化的能力**。

## 四、技术与商业启示

### 对语言和 API 设计

- 设计可“降级”或可提供默认值的参数（如 `context.Background()`）是降低变化传播成本、避免“类颜色”传染的有效手段。
- 语言特性应区分“可封装的变化”与“不可封装的变化”：前者是正常参数或依赖注入，后者才是需要谨慎引入的颜色特性。

### 对工程实践

- 在大型代码库中，变更管理的核心是**最小化穿透层数**。如果某项修改经常需要一路改到顶层，说明封装边界可能设计不当，或者该特性本身带有“颜色”性质。
- 团队可以通过适配层、默认值、接口隔离等手段，将参数变化的传播范围限制在局部，从而降低维护成本。

### 对技术决策

- 当评估引入 `async`、`context` 或类似机制时，应问一个关键问题：**这个变化能否在中间层被安全地截断？** 如果能，它更接近普通参数；如果不能，它很可能是一种“颜色”，需要更谨慎地评估其传染性成本。
- 理解“颜色”的不可封装性，有助于在语言选型、框架设计和重构时做出更清醒的权衡。

## 五、结论

本文用“变化传播形状”这一简洁判据，清晰地区分了普通函数参数与函数颜色。`context.Context` 虽然表面上像颜色，但它提供了 `context.Background()` 这一“天然断路器”，使得变化可以在调用链的任意位置被封装，因此它不是颜色。真正值得警惕的颜色特性，是那些无法被局部隔离、强制穿透整条调用栈的变化。这一洞察不仅澄清了长期争论，也为 API 与语言设计提供了一个实用的思维工具。
